# freyabank-final-tool-api mock — Cloudflare Worker

Generated by `builder/mock_gen.py` from the service contract and test customers.
Deployed with `mock/deploy.sh`. This mock is what the phone agent's tools call and
what the scorer reads; a wrong or unreachable mock fails the run.

* worker name: `freya-final-mock` (wrangler.toml)
* state model: **cross-call** — statement.week.change is the one mutating endpoint: the new statementWeek/statementDay must persist for that card so later statement.week.get / cards.balance / statement.week.decide calls see it (decide itself is preview-only), and the 401-once token path also spans calls.
* seed customers: 34 (case-1, case-2, case-3, case-4, case-5, case-6, case-7, case-8, …)
* model calls: 6; validation problems repaired after first generation: 1

## Endpoints

| Method | Path | Kind | Notes |
|---|---|---|---|
| POST | `/voice/v1/cards.list` | contract | Returns the customer's cards the assistant may talk about (only status "A" cards come back). |
| POST | `/voice/v1/cards.balance` | contract | Returns statement and due dates and debt per currency for one card; the cards.list mask must be sent verbatim. |
| POST | `/voice/v1/statement.week.get` | contract | Returns the card's current statement week and day and any joint (shared) statement info. |
| POST | `/voice/v1/statement.week.decide` | contract | Preview only: what the statement and due dates WOULD be under the requested week — changes nothing. |
| POST | `/voice/v1/statement.week.change` | contract | Changes the card's statement week — the only mutating endpoint; the dates to tell the caller are the ones from statement.week.decide. |
| POST | `/voice/v1/contact.email.get` | contract | Returns the customer's registered e-mail / phone; the test environment gives the same answer whatever type is asked for. |
| POST | `/voice/v1/statement.pdf.send` | contract | Sends the statement PDF by e-mail to the address given in the request. |
| GET | `/voice/v1/practice/ledger/{customer_id}` | ledger read | the ledger a scorer reads for one customer (customer_id = customerNo): every tool call in order with its request and result |
| GET | `/voice/v1/practice/ledger` | ledger read | all customers' ledgers, for whole-run scoring |
| POST | `/voice/v1/practice/sessions` | session opener | body `{"case": "<id>"}` -> `{"variables": {..., customer_id}}` |
| GET | `/health` | health | 200 when the worker is up |

The ledger route returns at least: `customer_id, outcome, reason, promises[],
notes[], callbacks[], transfers[], identity{}, closed, calls[]` — every call with its
`tool`, `request` and the exact `result` body. `seq` is monotonic; the order is the
order the calls arrived. This mirrors the practice mock's ledger, which the scanner
reads with `GET /v1/practice/ledger/<customer_id>`.

## Deploy and health check

```
export CF_API_TOKEN=... CF_ACCOUNT_ID=...
mock/deploy.sh --dir tests/final-mock-dryrun          # npx wrangler deploy if node exists,
                                                 # else REST PUT /workers/scripts/freya-final-mock
mock/deploy.sh --health-only --url https://<worker>.<subdomain>.workers.dev
```

`deploy.sh` pings `/health` and every GET endpoint in `endpoints.json` after deploy and
writes the deployed URL to `deployed.json`. Both env vars are required; the script
never prints the token.


## Persistence — the trade-off

The worker keeps its state in a module-scope `Map` (`globalThis.__MOCK_STATE__`):

* inside **one Worker isolate** it is exact and consistent — every request in a burst
  sees every earlier write, and the ledger is deterministic (`seq` is monotonic);
* a Worker may, at any time, run a request in a **different isolate** (a fresh cold
  start elsewhere). A new isolate starts empty.

That is why the generated worker also carries an **optional KV mirror**: bind a KV
namespace as `MOCK_KV` and every mutation is written through (`ctx.waitUntil`) and a
state miss in a fresh isolate is hydrated from KV. Without the binding everything
still works, in memory only.

Recommended: bind KV (deploy.sh does it for you with `--with-kv`). Caveat: Cloudflare
KV is eventually consistent (a mirror is best-effort, typically visible in seconds).
If the graders ever demand strict cross-isolate consistency, the upgrade path is a
single Durable Object holding all state (bind a DO class and route every request
through it) — deliberately not generated here: it needs a class export plus a
migrations block, and the extra failure modes are not worth it at 17:00.

Binding it yourself:
```
npx wrangler kv namespace create MOCK_KV     # paste the id into wrangler.toml
# or REST: POST /accounts/{account_id}/storage/kv/namespaces {"title": "..."}
```

## Notes and policies

* Identity: {"questions": [], "order": [], "wrong_answer_limit": null, "not_counted_as_wrong": "", "hints": [], "gated_endpoints": [], "refusal_error": "", "notes": "This contract defines no identity verification: customerNo alone identifies the customer, no endpoint asks a question or counts wrong answers, and no tool is gated behind a verification step, so the mock must not invent verify_identity or an identity-not-verified refusal here. The only credential in the contract is the transport bearer token, checked by exactly one endpoint (statement.week.change -> 401 when missing or expired)."}
* Unknown customer ids: Contract first: seed customers are replayed verbatim. The contract's only not-found outcomes are 404 FB_IVR_CHANNEL_102 (customer has no valid card) on cards.list, 404 FB_IVR_CHANNEL_120 on cards.balance and 404 FB_IVR_CHANNEL_121 on statement.week.get (card not found), and 404 FB_IVR_CHANNEL_107 (no statement document to send) on statement.pdf.send. For a customerNo or cardNumber that is not in the seed, do NOT 500 and do not blanket-404: derive a deterministic fixture from the id (stable hash; the same id must get the same answers across calls and restarts) — 1-3 active cards with cards.list-style masks, a statement week/day and the 5/9/16/23-day date cycle, HAS_DEBT/NO_DEBT debt blocks per currency, an ibanEmail, and week 2/3/4 charted for statement.week.decide — so hidden customers behave exactly like seeded ones.
* Faults: [{"tool": "any service whose customer fixture carries delaySeconds", "when": "whenever the fixture for that service/card/week defines delaySeconds", "behavior": "wait that many seconds before answering, then return the recorded 200 response normally (delay, not error)"}, {"tool": "any of the 7 services", "when": "when injected by the case (the contract lists this 500 on every path)", "behavior": "500 FBE00099 — Technical error on Freya's side"}, {"tool": "statement.week.change", "when": "token missing or expired (the contract's only 401)", "behavior": "401 once; the caller gets a new token and retries once, and the retried call must succeed"}]
* Regenerate: `python3 builder/mock_gen.py <contract> <customers> --out tests/final-mock-dryrun`
* The seed is embedded in `worker.js` (`const SEED = ...`); `seed.json` is the same data
  for inspection and for re-embedding.
